# 第二版：可信、可解释的生活圈分析

Status: ready-for-agent

## 问题陈述

第一版已经完成从分析中心点、步行时间和民生设施类别配置，到等时圈、设施覆盖、服务盲区、体检评分和在线报告展示的演示闭环，也具备真实地图模式与本地快照模式。但是，用户目前仍无法把结果作为可靠的社区规划依据：真实模式的服务盲区尚未按民生设施类别和真实步行时间分别判断；体检评分在设施缺失时可能仍给出偏高分数；地址输入、地图选点和坐标输入没有形成一致的分析中心点交互；规划建议缺少具体位置、判断依据和预期改善效果；任务和报告在服务重启后会丢失；移动端布局、报告导出、自动化交付与真实对比验证也未达到完整产品和赛事交付要求。

用户需要第二版把现有演示闭环升级为可信、可解释、可复现的分析闭环，使每个服务盲区、体检评分和规划建议都能够追溯到明确的民生设施类别、空间位置、步行时间、数据来源和计算模式，并使评审方能够稳定运行、验证和导出结果。

## 解决方案

第二版将产品定位为“可信分析版”，继续聚焦广州市黄埔区单城市样例，不扩张为多城市运营平台。系统将以分析中心点为起点，针对用户选定的每类民生设施分别计算真实步行可达性，在统一网格上识别重点服务盲区、设施稀疏区和正常覆盖区，并以可解释的数量、最近步行时间和空间分布子分数生成体检评分。

用户可以通过地址候选、地图选点或坐标输入确定分析中心点，运行演示模式或分析模式，查看每个区域的分类结果和判定依据。系统将结合盲区位置生成具体规划建议，并允许用户添加候选设施进行改善效果模拟。分析任务、报告和缓存将保存到 SQLite，以支持历史查看、重新运行和结果对比。报告支持 JSON、CSV、GeoJSON 和 PDF 导出，并在桌面端和移动端提供完整可用的交互。

真实地图调用将采用候选预筛选、批量或受控并发步行计算、坐标对缓存、限流重试和部分失败降级。任何真实 API、缓存、本地快照、空间插值或降级估算的使用都会记录为数据质量信息，避免将非真实测算结果描述为真实地图结果。

## 用户故事

1. 作为社区规划人员，我希望搜索地址并从候选结果中选择准确位置，以避免自由文本歧义导致分析中心点错误。
2. 作为社区规划人员，我希望在地图上点击确定分析中心点，以便在不知道准确地址时也能开展分析。
3. 作为专业分析人员，我希望直接输入经纬度，以便根据已知坐标复现分析结果。
4. 作为用户，我希望已选地址、坐标、地图标记和报告中的分析中心保持一致，以便始终清楚当前分析的地点。
5. 作为用户，我希望地址无法解析或超出当前样例范围时看到明确提示，以避免误分析。
6. 作为用户，我希望选择 10、15 或 20 分钟步行阈值，以便比较不同可达性标准。
7. 作为用户，我希望选择演示模式或分析模式，以便在更快反馈和更高边界稳定性之间做取舍。
8. 作为用户，我希望选择参与分析的民生设施类别，以便报告符合当前规划问题。
9. 作为用户，我希望未选择任何民生设施类别时系统阻止提交，以确保评分有意义。
10. 作为社区规划人员，我希望每类民生设施独立分析，以避免附近药店掩盖小学或菜市场缺失的问题。

## 实现决策

- 第二版继续采用单上下文的 Vue、TypeScript、Vite 前端和 FastAPI 后端，优先深化现有模块，不引入新的应用或微服务边界。
- 本版本属于 A 级版本需求，因为它会改变核心分析规则、持久化模型、报告契约和主要用户流程。
- 公开分析任务边界继续作为主测试缝：提交分析请求、轮询任务状态、获取完成报告。现有分析接口在可行情况下保持兼容，避免无必要的调用方迁移。
- 分析请求继续包含分析中心、步行阈值、分析模式和民生设施类别。空类别选择和无效坐标必须被校验拒绝。
- 分析中心在应用状态中只保留一份，包含 BD-09 坐标和展示地址。地址选择、地图选点、坐标输入和报告输出都读写该状态。
- 前端增加地址候选选择、地图点击选点、坐标输入和逆地理编码确认。离线快照模式不伪装支持任意地址，而是使用明确的样例位置或提示真实地理编码不可用。
- 服务区域分析使用统一分析网格，但每个选定民生设施类别单独进行分类。
- 直线距离只用于候选预筛选。真实 API 可用时，最终的正常覆盖、稀疏区或重点盲区分类必须基于最近同类设施的步行结果。
- 重点服务盲区表示：最近同类设施超过配置的步行阈值，且配置的周边范围内缺少同类设施。设施稀疏区表示局部设施数量不足，但仍在步行阈值内可达。报告记录两种条件及其证据。
- 服务区域输出继续使用 BD-09 坐标的 GeoJSON。每个要素包含区域类型、设施类别、阈值、最近设施标识、步行时间、步行距离、计算依据、数据来源和置信度信息。
- 等时圈继续采用径向采样，并保留演示模式和分析模式两档精度。分析模式提高方向采样数和边界细化次数。采样失败必须记录为数据质量事件，不能静默丢弃。
- 真实地图调用分为候选发现、直线距离预筛选、步行计算和报告组装阶段。步行计算优先使用批量距离能力，否则使用受控并发，并保证外部结果语义一致。
- 坐标对缓存保存起点、终点、出行方式、数据来源、创建时间和有效期。缓存只是内部优化，除数据来源元信息外不能改变报告契约。
- API 调用使用并发限制、有限退避重试、超时处理和明确的限流分类。单个类别失败时可生成部分报告，但失败类别必须排除在有效综合评分之外并明显提示。
- SQLite 保存分析任务、请求参数、任务状态、报告、数据质量事件和步行缓存。任务状态继续使用排队中、运行中、已完成、已失败。服务异常重启后发现的运行中任务必须被标记为中断或安全恢复，不能永久停留在运行中。
- 任务进度对应有意义的阶段：请求校验、中心点解析、设施发现、步行计算、区域分类、评分生成和报告组装。
- 类别评分保留数量、最近步行时间和空间分布三个组成部分。没有有效设施的类别不能获得正的步行时间分数，并区分输入缺失、计算失败和真实覆盖较差。
- 综合分只从有效的已选类别计算，并记录实际采用的权重。有效类别不足时，报告标记为部分结果，不展示具有误导性的综合分。
- 规划建议由类别级区域和评分结果生成。每条建议包含类别、优先级、目标区域引用、解释、候选位置（如有）和预计改善指标。
- 规划模拟以报告级场景实现，使用假设设施点重新计算受影响的覆盖、区域和评分，但不修改来源设施数据集。
- 报告契约包含标识和时间、请求参数、分析中心、等时圈、设施、类别级服务区域、汇总指标、类别评分详情、规划建议、模拟结果和数据质量事件。
- 报告历史支持列表、查看和重新运行。比较范围限制为两份已完成报告，展示评分、可达面积、设施数量和区域数量差异。
- 导出格式为：JSON 完整报告、CSV 表格数据、GeoJSON 空间图层、PDF 可读摘要。每种导出都包含或引用同一报告标识和分析参数。
- 前端保留现有桌面工作台结构。小屏幕上地图成为主区域，分析控件移动到底部抽屉，报告成为独立的可展开面板。
- 地图图层支持独立控制等时圈、各民生设施类别、设施稀疏区、重点服务盲区和规划候选点的显示。
- 数据质量说明控件打开可读的来源混合、失败情况、插值、缓存使用和置信度说明，不再只是无功能图标。
- 在可行情况下按主要依赖或页面拆分前端包，避免随着 PDF、地图和图表能力增加而持续扩大初始包体积。
- 持续集成运行后端测试、前端类型检查、前端构建、前端测试和容器构建或冒烟测试。默认 CI 不需要 API 凭证，因为本地快照模式可复现。
- 更新文档，说明 API 调用策略、等时圈生成、POI 归一化与去重、区域分类、评分、降级行为、部署和真实社区对比研究。
- 现有关于 Vue/FastAPI 架构、BD-09 交换格式、真实与本地快照模式、演示与分析精度、SQLite 持久化方向和固定规则评分的 ADR 继续有效。本规格用于完成已延后或部分实现的决策，不替换已有架构决策。

## 测试决策

- 测试验证外部可观察行为和领域结果，不绑定私有辅助函数实现。好的算法测试应提交已知设施和步行结果，并验证区域分类、评分解释和报告质量元信息。
- 最高层且主要的测试缝是公开分析 API：使用分析请求创建任务，观察任务状态变化，并验证完成报告契约。该测试缝以最少的实现耦合覆盖请求校验、分析编排、持久化和报告组装。
- 现有 FastAPI 测试客户端对健康检查、地图配置和分析创建已有覆盖，第二版在此基础上扩展确定性场景夹具，而不是改为绑定内部函数的测试。
- 地图提供方通过可替换的提供方边界返回确定性地理编码、设施检索和步行结果。默认测试套件不调用真实百度地图 API。
- 区域分类场景覆盖：没有同类设施、设施在一公里内但超过步行阈值、设施在一公里外但步行阈值内可达、正常覆盖、多类别同一网格和部分步行结果失败。
- 评分场景覆盖：零设施、一个近距离设施、多个分布良好的设施、步行数据缺失、类别部分失败、不同类别选择组合和权重总和。
- 等时圈场景验证多边形闭合且有效，演示模式和分析模式使用预期精度等级，并将失败采样记录到数据质量输出。
- 持久化测试创建任务和报告，重新初始化存储层后验证任务状态、参数和报告仍可获取。缓存测试验证命中、未命中、过期和来源元信息，不断言具体数据库实现。
- 重试和降级测试模拟超时、限流、格式错误和设施检索部分失败，验证有限重试、最终任务状态以及用户可见的数据质量说明。
- 规划建议测试验证建议引用实际类别级服务盲区，且不会根据无关设施类别生成建议。
- 模拟测试添加假设设施，验证来源设施数据未被修改，同时场景评分和服务区域按假设设施变化。
- 导出测试使用一份标准完成报告，验证 JSON 保留完整契约、CSV 包含预期表格行、GeoJSON 包含有效空间要素、PDF 包含关键汇总、参数和质量披露。
- 前端集成测试覆盖从选择分析中心、运行分析、查看区域说明到打开完成报告的可见用户流程。网络请求在公开 API 边界进行桩替换。
- 前端组件测试覆盖类别选择校验、进度和失败状态、图层开关、质量说明、历史任务选择和报告比较。
- 响应式测试验证桌面工作台和至少一个移动端视口。移动端重点验证没有横向溢出、控件抽屉和报告面板可用、地图仍为主要区域。
- 可访问性检查验证可访问名称、键盘可达性、焦点顺序，以及加载、错误和完成状态的提示。
- 持续集成在后端测试失败、前端类型错误、前端测试失败、生产构建失败或容器冒烟测试失败时阻断交付。
- 可选的真实接口集成测试只在提供凭证时运行，不作为日常开发或拉取请求验证的必要条件，并且不得记录凭证或敏感请求数据。
- 单独形成人工对比记录：固定一个黄埔区样例，记录分析日期和参数，将系统设施与服务盲区同人工地图核查结果比较，并说明差异和已知限制。

## 不在本规格范围内

- 多城市管理、城市级租户管理和全国数据运营。
- 登录、注册、用户角色、组织权限和协同编辑。
- 原生移动应用或独立小程序；本版本只要求响应式 Web 行为。
- 机器学习评分或不可解释的推荐模型；第二版继续使用可解释的规则评分。
- 实时人口、房产、人口统计或个人位置数据接入。
- 驾车、骑行或公共交通可达性分析。
- 自动建设预算估算、用地审批或最终公共政策决策。
- 超过两份报告的比较和大规模多社区排名。
- 除非性能证据证明现有任务模型无法支撑要求，否则不替换 SQLite 为 PostgreSQL、Redis、Celery 或分布式任务平台。
- 对任意地址提供完整离线分析；本地快照模式仍限于内置且明确标识的演示案例。
- 初始第二版交付不扩展四类核心民生设施；养老服务、便利店、托育、公园等类别在核心模型稳定后再考虑。

## 补充说明

- 推荐交付顺序为：第一阶段修正类别级服务盲区和评分行为；第二阶段完成分析中心交互、API 优化、持久化和可解释规划建议；第三阶段完成导出、移动端、持续集成和真实对比报告。
- 第一个实现里程碑不应增加新的产品范围，必须先用确定性测试保护零设施评分和类别级步行分类。
- 性能目标应分别测量本地快照模式和真实 API 模式。报告应暴露实际耗时以及 API/缓存使用情况，以便后续优化有数据依据。
- 当前桌面端视觉方向适合第二版。产品投入应优先放在正确性、可解释性和响应式行为，而不是重新设计视觉风格。
- 完成定义：评审人员能够选择或输入分析中心，在无凭证时运行离线演示，在配置凭证后运行真实分析，查看每个服务盲区和评分背后的证据，模拟一个候选设施，重新打开持久化报告，导出结果，并通过文档化命令复现构建和测试。
