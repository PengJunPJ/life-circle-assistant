## 结论

当前项目已经具备可展示的完整产品闭环：Web 工作台、百度地图坐标转换/地理编码/POI/步行算路、等时圈、服务盲区、评分、可解释建议、模拟、AI 解读、导出、Docker 和自动化质量检查都已存在。当前 `main@3cf8553` 的完整 `make quality` 在 2026-10-09 复验通过：后端 125/125、前端 46/46、Ruff、ESLint、TypeScript、生产构建、Docker 健康检查、离线分析和 PDF 导出均成功。

但当前状态不应直接对外宣称“已完全满足参赛要求”，也不建议按现有材料立即提交。主要原因不是功能缺失，而是下列交付断点：

1. 官网必交的作品介绍 PDF 和演示视频链接尚未形成，报名确认/邮件提交状态也无仓库证据；官网当前截止时间为 **2026-10-16 24:00**。
2. 参赛版本未唯一化：GitHub `main@3cf8553`、Gitee `master@2efb9ad` 和 `v2.2.0@6e9c902` 是三个不同快照，但应用和参赛文档仍声称 `2.2.0` 为当前评审版本。
3. `v2.2.0` 标签不包含后续的 WGS84/GCJ-02 → BD-09 坐标转换，也不是当前 Nginx 生产静态容器交付；它不能同时支撑当前 README/证据索引中的全部声明。
4. 命题要求“多源 POI 数据清洗策略”，当前实际上只是百度单数据源下的多关键词检索、语义归一和同址去重；文档标题写“多源”但未给出跨数据源的标识对齐、冲突、时效性和来源优先级策略。
5. 沙涌长盛花园 64/64 是“百度同源+同规则”复核，100% 一致不是独立真值验证；目前尚缺可支撑“真实对比测试”的跨源或现场证据。
6. 官网通用评分中“开源治理 20% + 长期发展 20%”尚未被现有证据包对标；仓库中没有 CONTRIBUTING、GOVERNANCE/MAINTAINERS、SECURITY、ROADMAP、依赖许可清单或已发布 SBOM。
7. 依赖安全不能以“工作流绿色”作为通过证据。当前 npm 官方审计是 2 critical / 1 high / 2 moderate；`pip-audit` 以退出码 1 报告 4 个受影响包、101 条原始告警记录。安全工作流目前刻意不因漏洞退出 1 而失败，因此“成功”只表示审计报告已生成。

## P1：对得分影响很大，建议提交前完成

### 1. 开源治理和长期发展几乎没有证据化

官网通用评分将开源治理和长期发展各列 20%。当前有 Apache-2.0、文档、ADR 和 CI，但缺少：

- `CONTRIBUTING.md`：环境、分支/提交/评审规范；
- `GOVERNANCE.md` 或 `MAINTAINERS.md`：决策、维护者和发布职责；
- `SECURITY.md`：漏洞报告和支持版本；
- `ROADMAP.md`：赛后 3/6/12 个月计划、数据合作和社区扩展；
- issue/PR 模板、CODEOWNERS、贡献者入门问题；
- 第三方依赖许可清单/NOTICE/SBOM 可下载物。

发布工作流宣称可生成 SBOM/provenance，但 GitHub Releases 当前为空，因此尚无已发布成果可验证。

### 2. 技术创新需要“对比证明”，不是功能罗列

已有可用的创新点：批量算路分块、扇形采样+二分边界、缓存/限流/重试/降级、证据约束 AI、可解释盲区与模拟。但现有材料没有将它们与“直线圆+简单 POI 计数”基线系统做统一对比。

建议在作品介绍 PDF 中用一页对比固化：

- 路网等时圈 vs 直线半径圈；
- 批量算路 vs 逐对请求（已有约 8 分钟 → 124 秒的历史数据）；
- 数据质量显式披露 vs 隐藏降级；
- 规则评分+证据引用 AI vs 自由生成文案。

每个对比必须带同一提交、同一环境、同一请求参数，不应只写“更智能”。

### 3. 站在评委视角重写三类命题硬指标

命题明确点名菜市场、药店、小学的 1 公里盲区。项目当前以四类核心网格+七类综合评分展示，这是产品增强，但容易模糊官方口径。

建议增加或在作品 PDF 单独呈现“赛题硬指标”面板：只汇总菜市场/药店/小学的 48 个类别网格、盲区数、证据和验证结果；医疗和其他三类标记为“产品扩展”。

### 4. 截图和演示证据仍是空的

`docs/contest/screenshots/README.md` 的 12 组图全部为待采集。截图不是官网单列的必交件，但是作品 PDF、视频、README 首屏和产品体验打分的直接证据。应至少保留：

- 真实底图+等时圈+网格+设施点的完整画面；
- 真实步行折线；
- 命题三类盲区证据；
- 执行指标和数据质量；
- 评分、雷达图、AI 证据引用和模拟前后；
- 离线/真实模式的明显标识。

### 5. 仓库门禁存在但不强制

- GitHub `main@3cf8553` 的最新质量工作流确实成功，后端/前端/容器三个 job 均成功：<https://github.com/PengJunPJ/life-circle-assistant/actions/runs/37879566787>。
- GitHub 公开 API 显示 `main.protected=false`，仓库 rulesets 为空；因此当前是“有 CI，无强制合并门禁”。
- Gitee 主分支不含 GitHub `main` 后续增加的安全/发布工作流，Gitee Go 也未实跑。

命题只要求 GitHub Actions 或 Gitee Go 等 CI/CD，所以如将 GitHub 作为官方参赛仓库，现有 Actions 已覆盖该基础得分点；Gitee Go 并非另一个官方必做项。但建议启用 GitHub `main` 保护，要求“质量门禁汇总”和必要安全检查；如最终提交 Gitee 链接，则必须先同步并在 Gitee 上实跑等价门禁。

### 6. 演示路径的时间和文案需要实际走通

本次从干净 Docker 离线环境执行默认“正式分析”，页面报告的总耗时为 51.77 秒，且这是离线提供方、0 地图 API 调用的场景。界面视觉完成度高，但现有“离线路径约 3 分钟”的录屏计划需要预留等待或改用“快速分析”。

同时发现明确文案错配：默认中心显示“黄埔区红山街道海韵东路离线样例中心”，说明文字却写“离线快照仅支持萝岗样例范围”。这会直接损害数据可信度，应在截图/录屏前修正并加测试。

### 7. 文档和当前实现已有漂移

- `v2.2.0` 发布说明的发布后待办仍写“将前端容器从 Vite 开发服务器调整为生产静态构建”，但当前 HEAD 已使用 Nginx；
- 当前实测为 125+46，发布说明是 112+44；
- 性能表仍基于 2.1.1 和旧提交，可作历史证据，但不应不标版本地代表新 tag；
- `evidence-index.md` 把单源归一标为“多源 POI”已满足，这一状态需要修正。

## 不能对外宣称的内容

在完成对应证据前，不应宣称：

- “所有参赛材料已完成”——作品 PDF、视频和外部提交回执尚无。
- “`v2.2.0` 就是当前全部能力的参赛版本”——tag 不含坐标转换和当前容器交付。
- “已完成多源 POI 融合”——当前是单源多关键词归一。
- “盲区准确率 100%”——当前仅是同源同规则 64/64 一致。
- “安全扫描通过，无高危依赖”——工作流主动放行了 audit 退出 1。
- “主分支保护已生效”——GitHub 公开 API 显示 `protected=false`。
- “Gitee Go 已落地”——尚未实跑。
- “真实地图 API 可用性由 CI 持续验证”——CI 仅跑离线/注入提供方，真实 API 是受控人工流程。
