# 赛事交付差距收口：从功能型 Beta 到可验收参赛版本

Status: ready-for-agent

## 问题陈述

当前项目已经完成了参赛题目要求的大部分核心功能：它提供 Web 工作台，支持地址、地图和坐标选点；能够在真实百度地图模式下调用地理编码、逆地理编码、POI 检索和步行路线；能够生成 15 分钟步行等时圈，按民生设施类别计算服务区域，识别重点服务盲区和设施稀疏区，并生成评分、规划建议、候选设施模拟和可视化报告。项目还具备本地快照、SQLite 持久化、缓存、限流、重试、降级、导出、响应式界面、Docker 和自动化测试等工程基础。

但与赛题的完整交付要求和“开源 AI 工具赛道”的评审语境相比，项目还存在几类会直接影响评审结果的差距：

- AI 能力目前仍停留在产品规划层，尚未在报告之上提供可演示、可解释且有证据约束的 AI 解读能力；
- 真实社区核查已经有报告和首个全网格标注材料，但 64 个类别网格仍处于人工核查草稿，尚未形成可对外公布的准确率、召回率、F1 或混淆矩阵；
- 当前离线快照明确是合成样例，历史核查还暴露过中心点地址、设施语义和真实场景错配问题，因此不能把离线分数或盲区直接当作真实社区结论；
- GitHub Actions 配置和本地质量命令已经存在，但主远端是 Gitee，Gitee Go 流水线、PR 检查项和保护分支门禁尚未完成开通、实跑和绑定；
- API 策略、等时圈算法、POI 清洗、盲区识别和对比核查文档已有基础，但还需要整理成评审人员可以从干净环境一键复现的最终证据包；
- 评分、图表、地图图层、规划模拟和数据质量展示已实现，但“真实路网等时圈”与“离线/降级结果”的证据边界必须在演示脚本、报告和现场流程中保持一致。

因此，本规格不是重新开发 V2 核心功能，而是收口赛事要求中尚未达到“可验证、可复现、可对外陈述”标准的部分，并明确哪些能力已经满足、哪些能力只能算部分满足、哪些能力必须继续实现。

## 解决方案

建立一份以赛题要求为基线的交付验收闭环，分四条工作线推进：

1. **AI 赛道能力**：在结构化体检报告上增加可解释 AI 规划助手，支持摘要、盲区解释、规划问答和汇报摘要。AI 只能读取报告及其数据质量信息，所有事实性结论必须引用报告实体；无模型密钥时使用规则模板降级，不能影响原始空间分析。
2. **真实社区证据**：固定一个地址语义与坐标一致的黄埔区样例社区，完成四类设施、全部网格的独立人工核查，生成可审计的准确率、精确率、召回率、F1、宏平均和混淆矩阵；在条件允许时再补充 3～5 个社区，区分单社区结果和汇总结果。
3. **工程门禁与复现**：保留本地 `make quality`、GitHub Actions 和 Docker 冒烟作为代码质量基线；在 Gitee 上完成不依赖 Docker Compose 的 PR 质量流水线、实际检查项登记和 `master` 保护分支门禁验证。Docker Compose 多容器检查只在明确提供 Docker daemon 的执行资源中作为独立验收，不凭配置文件推断已生效。
4. **最终参赛证据包**：把真实模式演示、无凭证离线演示、API 调用策略、等时圈算法、POI 归一化、盲区规则、性能指标、质量限制、许可证、环境变量脱敏和已知限制整理为一套可复制的评审流程，避免评审人员只能依赖开发者口头解释。

当前能力基线如下：

| 赛题要求 | 当前状态 | 差距判断 |
| --- | --- | --- |

| 开源 AI 工具赛道中的可演示 AI 能力 | 尚未满足 | 需要落地可解释 AI 规划助手 |

## 用户故事

1. 作为评审人员，我希望能从干净环境启动 Web 应用，以便不依赖开发者本机状态判断项目是否可运行。
2. 作为评审人员，我希望在没有百度凭证时运行一个明确标记的离线样例，以便快速验证完整交互闭环。
3. 作为评审人员，我希望在配置百度凭证后切换真实模式，以便确认系统确实调用地理编码、POI 和步行路线能力。
4. 作为评审人员，我希望看到浏览器底图状态、服务器地图服务状态和数据来源标识，以便区分真实地图、缓存和本地快照。
5. 作为社区规划人员，我希望输入地址、点击地图或输入坐标确定分析中心，以便使用适合当前场景的选点方式。
6. 作为社区规划人员，我希望系统生成真实路网 15 分钟步行等时圈，而不是仅生成圆形直线距离缓冲区。
7. 作为社区规划人员，我希望看到菜市场、药店、小学和医疗服务的覆盖情况，以便理解基础生活服务是否齐全。
8. 作为社区规划人员，我希望地图用不同图层标识正常覆盖区、设施稀疏区和重点服务盲区，以便快速定位优先问题。
9. 作为社区规划人员，我希望点击网格后看到最近同类设施、步行时间、步行距离、分类依据和数据来源，以便核验系统判断。
10. 作为社区规划人员，我希望评分可以展开查看数量、步行时间和空间分布子分，以便判断综合分是否合理。
11. 作为社区规划人员，我希望看到规划建议引用具体类别和网格，而不是得到没有空间证据的泛化建议。
12. 作为社区规划人员，我希望添加候选设施并查看模拟前后的覆盖和评分变化，以便评估规划动作的潜在价值。
13. 作为用户，我希望历史报告、重新运行、报告比较和 JSON/CSV/GeoJSON/PDF 导出都能保留分析参数和数据质量信息，以便复盘和汇报。
14. 作为评审人员，我希望看到系统如何处理 POI 多关键词检索、同址机构归并和重复设施，以便评价地图 API 使用深度。
15. 作为评审人员，我希望看到系统如何处理 QPS 限流、超时、部分失败、缓存命中和降级估算，以便评价工程可靠性。
16. 作为评审人员，我希望看到真实 API 调用量、批量/并发策略、缓存命中率和阶段耗时，以便判断优化是否有实际效果。
17. 作为评审人员，我希望真实社区的中心地址、坐标、核查日期和设施类别口径一致，以便相信对比测试结论。
18. 作为人工核查人员，我希望使用不包含系统预测分类的盲审网格模板，以便避免先看答案造成确认偏差。
19. 作为人工核查人员，我希望逐格记录设施、有效步行路线、道路障碍、核查来源和日期，以便后续复核人工真值。
20. 作为评审人员，我希望看到完整网格的准确率、精确率、召回率、F1、宏平均和混淆矩阵，以便判断盲区识别是否可靠。
21. 作为评审人员，我希望单社区指标与多社区汇总指标分开显示，以免小样本结果被误解为普遍准确率。
22. 作为用户，我希望离线快照明确标记为合成样例，以免把演示设施、地址和分数误认为实时社区事实。
23. 作为用户，我希望真实报告中披露 API、缓存、插值和降级估算的混合情况，以便知道哪些结论可以直接用于现场讨论。
24. 作为开源 AI 赛道评审人员，我希望系统能对体检报告生成摘要，以便快速理解社区主要问题。
25. 作为开源 AI 赛道评审人员，我希望 AI 能解释某个盲区为什么被判定为重点服务盲区，以便看到 AI 与地图事实的结合。
26. 作为规划人员，我希望询问优先补充哪类设施，并得到带证据的回答，以便辅助方案排序。
27. 作为报告阅读者，我希望 AI 引用报告中的网格、设施、评分和模拟结果，而不是编造不存在的实体或数字。
28. 作为评审人员，我希望没有模型密钥时仍能展示规则模板降级结果，以便离线复现 AI 功能。
29. 作为用户，我希望模型错误不会破坏原始体检报告，以便 AI 只是增强层而不是单点故障。
30. 作为维护人员，我希望 API 密钥只在后端使用，且不会出现在页面、日志、导出和提交记录中，以便安全交付。
31. 作为维护人员，我希望每个 PR 都能自动运行后端测试、前端检查和构建，以便减少回归。
32. 作为仓库维护者，我希望 `master` 保护分支要求质量检查成功后才能合并，以便门禁不是“配置存在但未生效”。
33. 作为参赛团队，我希望 README、许可证、环境变量、Docker、测试和真实对比报告可以按固定顺序打开，以便评审人员快速找到证据。
34. 作为参赛团队，我希望最终演示流程不需要手工解释隐含前提，以便不同评审人员都能复现同一条路径。

## 实现决策

- 本规格定义为赛事交付收口需求，优先补齐可验证性、AI 赛道匹配度和工程门禁，不重写已经稳定的地图分析核心。
- 继续使用当前 Vue、TypeScript、Vite、FastAPI、SQLite、Docker Compose 和可替换地图提供方边界；不因为赛事收口引入新的微服务或分布式任务平台。
- 公开分析 API、报告契约、地图提供方、报告导出和基准评估工具继续作为现有稳定边界。新增功能必须保持 V2 报告字段兼容，不得为了 AI 或基准指标删除既有字段。
- AI 能力采用“结构化体检报告 → AI 解读服务 → 结构化 AI 结果”边界。AI 仅解释报告已有事实，不负责地理编码、POI 检索、步行计算、等时圈、评分或盲区分类。未配置模型时使用规则模板，真实模型通过后端适配器可选接入。
- 真实社区基准必须先固定中心点地址语义、BD-09 坐标、核查日期、步行阈值、设施类别、网格规则和数据来源，再进行盲审。基准状态在所有网格完成前保持 `draft`，不得输出对外准确率。
- 首个基准覆盖 4×4 网格与四类设施，共 64 个类别网格；每格记录人工分类、证据来源、核查时间、核查人和道路障碍说明。评估结果至少包含准确率、精确率、召回率、F1、宏平均和有效预测覆盖率。
- 真实报告、离线快照和人工真值必须显式区分。合成快照不作为真实社区指标；真实报告若混合缓存或降级估算，必须在报告和演示中披露，并限制其结论表述强度。
- 对外展示的样例社区只能使用地址、设施和坐标语义一致的数据集。若旧快照与实时地址或设施场景不一致，应重新抓取、重新命名或从真实结论中剔除，而不是继续沿用历史名称。
- 地图调用策略继续采用逐关键词 POI 检索、UID/规范化名称/坐标去重、直线预筛、批量或受控并发步行计算、缓存、限流、有限重试和部分失败降级；最终交付文档必须给出实际调用量和耗时证据。
- 等时圈继续使用径向采样和边界细化，且将真实路网结果与插值/降级边界分开标识。评审演示应至少展示一次完整真实模式和一次无凭证快照模式。
- 评分和盲区规则保持可解释、确定性和可审计。AI 不得改变分数、服务区域或人工基准的预测值；AI 结果与原始报告视觉和数据结构上分离。
- CI/CD 分两层落地：代码仓库中的 GitHub Actions 和本地质量命令作为可复现基线；Gitee Go 只将实际在当前仓库运行过的检查纳入保护分支门禁。若 Gitee 托管环境不提供 Node 22、Python 3.12 或 Docker Compose，不降级项目运行时，而是把 Docker 检查放到匹配运行时的自有执行资源或独立验收环境。
- Gitee 门禁必须经过一次成功 PR、一次故意失败 PR 和一次修复后恢复的反向验证，才能在文档中标记为已落地。仅提交 YAML、仅显示流水线存在或仅有 GitHub Actions 不算 Gitee 门禁完成。
- 最终交付材料以评审顺序组织：项目定位与 AI 价值、启动命令、离线演示、真实模式配置、核心地图能力、算法与 API 策略、真实社区基准、工程质量、已知限制和许可证。所有示例凭证必须脱敏，真实 AK/Secret 不进入报告、截图、日志或版本库。
- 本规格不把“提交报名表、上传视频或填写外部赛事系统”当作代码仓库自动完成的事项；如赛事平台另有材料要求，应在交付清单中记录为人工步骤。

## 测试决策

- 测试验证评审人员能观察到的交付行为和证据，不绑定私有函数、模型提示词措辞或具体 CI 插件实现。
- 本规格采用一个主要高层测试缝：**竞赛交付验收流程**。从干净环境启动容器，运行无凭证离线分析；在显式配置凭证时运行一次真实百度分析；验证地图、等时圈、服务区域、评分、导出、数据质量和执行指标；随后运行基准评估、质量门禁和证据包检查。
- 离线验收验证无需外部凭证即可启动，首次使用引导可完成中心点确认和分析，报告可展示图表、地图图层、评分、规划建议、模拟、历史和导出。
- 真实验收使用可替换或录制的确定性夹具保护日常测试；只有专门的人工或受控集成流程调用真实百度 API。真实流程验证地理编码/逆地理编码、逐词 POI、步行路线、QPS 限制、缓存和数据来源标识，禁止输出凭证。
- 报告验收验证等时圈是闭合有效几何、服务区域包含三种分类、设施类别分开计算、盲区证据可展开、评分在缺失或部分失败时不产生误导性综合分，导出格式均保留参数和质量说明。
- 基准验收验证人工模板不带系统预测分类、64 个网格全部标注后才可转为 `verified`，未完成时工具拒绝生成对外完整指标；评估输出与人工证据的网格集合一致。
- AI 验收验证摘要、盲区解释、规划问答和汇报摘要都引用当前报告实体；未知设施、网格、分数或步行时间被拒绝或降级；无模型、超时、无效 JSON 和限流不会破坏原始报告。
- 性能验收验证报告中记录 API 调用量、缓存命中率、重试/限流/超时、各阶段耗时和总耗时；性能数据必须区分快照模式与真实 API 模式，不能用离线速度代替真实性能声明。
- 开源交付验收验证许可证存在、环境变量示例为空或脱敏、Docker Compose 配置可解析、一键质量命令可执行、前后端测试和生产构建通过，且仓库不包含百度 AK、Secret 或模型密钥。
- CI 验收验证 GitHub Actions 或本地等价质量流程能阻断失败提交；Gitee 门禁只有在实际 PR 检查成功、失败阻断和修复恢复三步均完成后才标记为通过。
- 真实社区对比只作为人工证据，不把单日、单中心、单地图提供方的结果外推为整体准确性。若基准未完成，报告必须显示“草稿”，不展示准确率或 F1 作为已验证成绩。

## 不在范围内

- 重新实现已经通过测试的百度地图调用、等时圈生成、设施归一化、评分、规划模拟、历史报告和导出功能。
- 将 AI 变成开放域聊天机器人，或让模型替代地图事实、步行路线、盲区分类和评分。
- 在本规格内建设多城市生产运营平台、账号权限、租户管理、协同编辑或人口/容量/预算/审批数据平台。
- 把离线合成快照包装成实时城市规划结论，或用单个社区的核查结果宣称系统具有普遍准确率。
- 在没有人工真值和独立证据的情况下自动“生成”准确率、召回率、F1 或排行榜成绩。
- 为了适配未经验证的 CI 托管环境而将生产运行时降级到旧版 Node/Python，或把 Docker Compose 能力假设为已存在。

## 补充说明

- 按赛事得分优先级，建议实施顺序为：先完成 AI 规划助手最小可演示闭环；再完成首个 64 网格真实基准并修正样例数据语义；随后完成 Gitee PR 门禁实跑；最后整理证据包和现场演示脚本。
- 当前项目已经足以展示“地图能力 + 空间分析 + 工程优化”的主体价值。剩余工作重点是让评审人员能验证结论，而不是继续堆叠更多设施类别或复杂模型。
- 赛题要求中没有硬性规定必须使用大语言模型，但项目处于“开源 AI 工具赛道”，增加有证据约束的 AI 解读层能明显改善赛道匹配度；AI 的可信边界和降级行为比自由聊天范围更重要。
- 当前红山街道海韵东路真实报告可以作为真实 API 能力和执行指标的证据，但对应人工基准在完成 64 格核查前只能标记为草稿。历史萝岗/红山语义错配材料应作为限制和修复记录，不作为最终成绩证明。
- 完成定义：评审人员能在无凭证环境跑通离线演示，在受控真实环境看到百度 API 和真实步行等时圈，查看四类设施覆盖与盲区依据，运行规划模拟，导出报告，看到 AI 摘要及证据引用，读取完整真实社区基准指标，执行自动化质量检查，并在仓库中找到许可证、部署、算法、API 策略和已知限制说明。
